# 利用枠の節約: 仕組みと判断の根拠

usage-audit のスキルが所見を説明するときの根拠です。Claude Code の公式ドキュメント（[How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)、[Subagents](https://code.claude.com/docs/en/sub-agents)）にもとづき、Claude Code 2.1.295 で確かめています。

## 消費の仕組み

Claude Code は、リクエストのたびに会話全体（システムプロンプト、ツールの定義、これまでのやり取り、ツールの結果）を送り直します。前回と同じ先頭部分は、プロンプトキャッシュから読まれます。

API の料金では、通常の入力を 1 としたとき、次の比率になります。

| 種類 | 比率 |
| --- | --- |
| キャッシュからの読み込み | 0.1 |
| 5 分キャッシュへの書き込み | 1.25 |
| 1 時間キャッシュへの書き込み | 2 |
| 出力 | 5 |

モデルの間にも差があります（API の料金で haiku : sonnet : opus がおよそ 1 : 3 : 5）。usage-audit は、この比率で重みを付けて、どこが重いかを比べます。

キャッシュには寿命（TTL）があり、読まれるたびに延びます。切れたあとのリクエストは、会話全体をもう一度書き込みます。

| リクエストの種類 | プランの枠内 | 枠を超えた分（usage credits）・API キー |
| --- | --- | --- |
| メインの会話 | 1 時間 | 5 分 |
| サブエージェント、compaction など | 5 分 | 5 分 |

TTL は 5 分と 1 時間の 2 種類だけで、1 時間より長くはできません。

## 節約の物差し

物差しは、次の 1 ターンの安さではなく、その仕事を最後までやりきったときの消費の総量です。

飛行機の燃費に例えると、測るのは「積荷を運んだ距離あたりの燃料」です。積荷（仕事に要る文脈）を降ろして飛距離を伸ばしても、燃費が良くなったことにはなりません。見るのは、同じ積荷を運ぶのに余計な燃料を使っていないか（キャッシュが切れたあとの書き直し、使い終わった大きな結果を運び続けること）です。一方で、燃料の少ない小さな機体を何機か飛ばして、同じ積荷をより少ない燃料の合計で運べるなら、それは節約です（軽いモデルのエージェントに分けて任せる、など）。

- 会話が長くなるほど、1 リクエストごとに読み込む量が増えます。消費の多くは、この読み込みの積み重ねです
- 新しいセッションに移ると 1 ターンは安くなりますが、作業に要る文脈はまた溜まります。消えた情報を説明し直す手間（読み直し、取り違え）は集計に出ませんが、総量を増やします。セッションを分けて得をするのは、作業の進み具合がファイルにまとまっていて、前の会話の経緯が要らないときです
- 効くのは、文脈に入るものを選ぶことと、リクエストの数を減らすことです

## 所見ごとの読み方

### メインの会話が大きい（main-context）

何が大きいかで処方が変わります。

- 一度しか要らない大きなもの（ドキュメントの全文、長い一覧、ログ、サブエージェントの長い報告）が入っているなら、入れない工夫を勧めます。調べ物はサブエージェントに任せて要点だけを受け取る、大きな出力はファイルに書かせて必要な部分だけを読む、WebFetch には答えだけを返させる問いを渡す、など
- 会話そのもの（相談や設計のやり取り）が大きいなら、それは仕事に要る文脈です。削ることは勧めず、リクエストの数を減らす工夫（ツール呼び出しを 1 ターンにまとめる、バックグラウンドの作業の終わりの通知を減らす）を勧めます
- 作業の区切りで、次の作業に前の経緯が要らないなら、`/clear` や新しいセッションも選択肢として示します。既定の処方にはしません

入れてから消すより、入れないほうが確実です。

自分（Claude）で内容をファイルに書き写すのは逆効果です。出力の比率は 5 なので、書き写す費用が、文脈から外して浮く分を上回りがちです。効くのは、ツールの結果のように、もともと Claude の出力ではないものをファイルに向ける場合です。

### キャッシュが切れたあとのメインの再開（main-idle）

1 時間以上あけて同じセッションに戻ると、会話全体を 1 時間キャッシュの比率（2）で書き直します。数十万トークンの会話なら、新しいセッションの開始時（数万トークン）より桁違いに重くなります。

- 1 時間以上あける再開が何度もあるなら、警告として伝えます。翌日や数時間後の続きは、新しいセッションで、要点を渡して始めるほうが軽くなります
- 翌日に古いセッションを開いて「引き継ぎ文を書いて」と頼むと、その 1 回で会話全体を書き直します。引き継ぎのメモは、区切る前（キャッシュが温かいうち）に書いてファイルに残しておくと、翌日は新しいセッションでそれを読むだけで済みます。メモにセッション ID を書いておけば、足りないことは古いセッションを開かずに、会話の記録（`~/.claude/projects/<プロジェクト>/<セッション ID>.jsonl`）から必要な部分だけ探して読めます
- 「このファイルを変えたのはどのセッションか、何のためか」を知りたいときも、そのセッションに聞くのではなく、記録を探します。ファイル名で記録を検索し、そのファイルへの Edit や Write と前後のやり取りだけを読めば、変更と理由が分かります。古いセッションに聞くと、答えるために会話全体を読み直します（キャッシュが切れていれば書き直し）。git で追えるファイルなら、`git log -p` が先です
- 1 時間以内の続きなら、切り替えは勧めません
- 前の会話の経緯が要る場合は、続けても構わないと添えます

### サブエージェントの再開（subagent-ttl）

サブエージェントのキャッシュは、プランの枠内でも 5 分です。結果を読んで考えている間に 5 分が過ぎ、そのあと SendMessage で同じエージェントに続きを頼むと、そのエージェントの会話全体を書き直します。

- 続きを頼むことが多いエージェントは、定義の frontmatter に次のように書くと 1 時間になります（v2.1.248 以降。SendMessage での再開にも効きます）

  ```yaml
  experimental:
    cacheTtl: 1h
  ```

- 1 時間の書き込みは 5 分より高い（2 と 1.25）ので、再開しないエージェントに付けると損です。5 分を超えてからの再開が 1 回でもあれば、多くの場合は元が取れます
- 次の場合は効きません。環境変数 `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` や設定 `subagentPromptCacheTtl` があるとき（そちらが優先）、プランの枠を超えて usage credits を使っているとき、組み込みのエージェント（定義を書き換えられない）
- 定義を作ったり変えたりしたら、セッションを開き直すまで反映されません
- 追加の質問を 1 回にまとめて聞くのも、同じくらい効きます

### エージェントのツールの許可が持ち込むもの（agent-tools）

サブエージェントは起動のたびに、自分のシステムプロンプトとツールの定義を書き込むところから始まります。そこに、ツールの許可に応じて次のものが足されます（Claude Code 2.1.295 での観察）。

| 定義の `tools` | 足されるもの |
| --- | --- |
| `Skill` を含む | 使えるスキルの一覧（名前と説明） |
| 書いていない（すべてのツール） | スキルの一覧に加えて、あとから読み込めるツールの一覧と MCP サーバーの説明 |
| `Skill` を含まない | スキルの一覧は足されない |

スキルの一覧は、入れているプラグインのスキルがすべて載るので、プラグインが多いほど大きくなります。足されたものは、そのエージェントの会話が続く限り毎回読み込まれるので、リクエストの多いエージェントほど効きます。

集計の `agentTypes[].startBreakdown` に、種類ごとの大きさ（`parts`）、所見の直し方で消える部分（`removable`）、範囲の中でそのエージェントが読み込んだスキル（`skillsLoaded`）が出ます。

- 定義に `Skill` があり、スキルを読み込んでいないなら、`tools` から `Skill` を外します。要る手順は、頼むときのプロンプトに書いて渡します
- スキルを読み込んでいるなら、外すかどうかは検討です。読み込んでいる内容をプロンプトで渡せるときだけ外します
- `tools` のない定義には、要るツールだけを並べた `tools` を書きます
- 組み込みのエージェント（general-purpose、Explore など）は書き換えられません。同じ役割の定義を、ツールを絞って自分で作ります

### スキルの一覧（skill-listing）

メインの会話にも、使えるスキルの一覧が入ります。プラグインのスキルは `<プラグイン>:<スキル>` という名前で並び、使わないスキルも全部載ります。長いセッションでは、同じ一覧が途中でもう一度入ることがあります（Claude Code 2.1.295 での観察）。入るたびに書き込まれ、そのあとのリクエストで毎回読み込まれます。

集計の `skillListing` に、開始時の大きさ、途中で入り直した回数（`reinjections`）、プラグインごとのスキルの数・文字数・範囲の中で使われた回数（`plugins`）が出ます。使われた回数は、Skill ツールの呼び出しと、スラッシュコマンドで数えます。

- 範囲の中で一度も使われていないプラグインを止めると、その分が一覧に入らなくなります。見込みの節約量は、そのプラグインの分だけです。`claude plugin list` に出るプラグインは、プロジェクトの設定で止められます。claude.ai のアカウントで有効にしたプラグインは claude.ai の設定で止めるので、ほかのプロジェクトにも効きます
- 名前に `<プラグイン>:` の付かないスキル（プロジェクトやユーザーのスキル）は、節約に数えません
- サブエージェントに入る一覧は agent-tools の側で数えます。同じ一覧を二度数えることはありません

### 単発のエージェント（skill-instead）

何度も起動されるのに、再開されず、会話もあまり育たないエージェントは、スキルにしたほうが安いことがあります。スキルはメインの会話に指示を足すだけで、メインの 1 時間キャッシュに乗ったまま動き、起動のたびの書き込みがありません。ただし、実行した結果はメインの会話に残ります。出力が大きい作業なら、スキルの frontmatter に `context: fork` を付けて、フォークで動かす方法があります。

### 高いモデルで動くサブエージェント（model）

定義の `model` を下げると消費は減りますが、品質に関わります。提案にとどめ、利用者が選んだときだけ変えます。

軽いモデルで動かしたい作業は、`model` を指定したサブエージェント（エージェント定義か、Agent ツールの `model`）にします。スキルの `model` は向きません。メインの会話で動くスキルに別のモデルを書くと、そのターンと、元のモデルに戻る次のターンで、会話全体をキャッシュなしで読み直します。`context: fork` のスキルは親の会話をまるごと引き継ぐので、モデルが違うと親の会話全体を新しく書き込みます。

### 大きなツールの結果（tool-results）

大きな Read や Bash の結果は、そのあと会話が続く限り、毎回読み込まれます。読む範囲を絞る（行の範囲、grep）、調べ物を軽いエージェントに任せる、といった直し方を勧めます。

## 直したあとの比べ方

`--by-session` の `perSession` と `--compare-at` の `compare` の数字は、どれも範囲の中のリクエストだけで数えます。

- ターン（`turns`）は、メインの会話で、利用者が新しく頼んで始まったやり取りの数です。セッションの最初のリクエストと、前のやり取りが終わったあとのプロンプトで始まったリクエストを数えます。ツールが動いている途中に送ったプロンプトは、そのやり取りの一部として数えます
- 作業の量はセッションごとに違うので、ターンあたり（`weightedPerTurn`）とリクエストあたり（`weightedPerRequest`）の重みで比べます
- 所見の `saving` はセッションごとに分けられます。`perSession[].findings` に、そのセッションでの見込みの節約量と、その所見の指標が出ます。`compare.byFinding[]` の `savingPerTurn` は、群ごとの見込みの節約量をターンの数で割ったものです

所見ごとに、前後で見る指標は次のとおりです（`compare.byFinding[]`）。

| 所見 | 見る指標 |
| --- | --- |
| `main-idle` | `rewriteTokensPerResume`（1 時間以上あけた再開 1 回あたりの書き直し）、`idleResumesPerSession`（その再開の回数） |
| `main-context` | `mainContextMedian`、`mainContextP90`（メインの文脈の中央値と、大きいほうから 10% の境目） |
| `agent-tools:<エージェント>` | `startContext`（起動時の文脈）、`listingReinjectionsPerRun`（スキルの一覧が入り直した回数） |
| `skill-listing` | `startListingChars`（開始時の一覧の文字数）、`reinjectionsPerSession` |
| `subagent-ttl:<エージェント>` | `write5mShare`（そのエージェントの書き込みのうち 5 分キャッシュの割合。`cacheTtl: 1h` が効けば 0 に近づく） |

どの所見にも、`sessionsWith`（その所見が当てはまったセッションの数）と `savingPerTurn` が付きます。

## 並列か一括か

同じ種類の小さな作業をいくつか、エージェントに任せるときの目安です。

- 1 本ずつ並列にすると、それぞれのエージェントが自分の会話全体を書き込みます。1 本にまとめると、開始時の部分を書くのは 1 回で済みます。小さな作業なら、まとめるほうが安いことが多いです
- バックグラウンドのエージェントは、終わるたびにメインの会話に通知が来て、メインが 1 ターン動きます。メインの会話が大きいときは、この通知のターンが重くなるので、本数が少ないほうが有利です
- まとめた 1 本の会話が大きく育つと、後の作業ほど前の作業の分まで読み込み直します。作業ごとに読む量が大きく、互いに関係のない作業は、並列にして会話を分けたほうが安くなる境目があります
